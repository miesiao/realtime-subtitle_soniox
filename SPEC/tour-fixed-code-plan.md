# 旅行團固定入場碼：流程規劃

狀態：固定入口 MVP 已在本機實作，尚未部署。2026-09-17。

## 目標與基本規則

團員在整趟旅程使用同一個 `/live?code=...` 網址或 QR。主辦方每天可以開多場；每一場各有開始／結束時間、點數用量、原始稿與整理稿。固定碼屬於「旅行團」，不屬於其中某一場。

目前系統的 `joinCode` 只指向一個場次；結束場次後，觀眾畫面會顯示「本場已結束」。因此不能單純重用單一場次，也不能只把新場次的隨機碼改成舊碼。

## 主辦方操作

1. 在「字幕場次」新增「建立固定入口」，填寫團名，例如「九州五日團」。系統配發不易混淆的 8 碼英數代碼、固定連結與 QR。建立時不扣點。
2. 將連結／QR 分享一次給團員。建立後主辦方可複製、下載或再次查看。團名可以改，代碼不會隨改名改變。
3. 每次活動從該團按「開新場」，填當場名稱，例如「9/18 上午導覽」。進入現有主持頁，按 Start 才收音與依現有規則扣點。
4. 按「結束本場」後，當場逐字稿獨立整理、下載，團員看到「本場已結束，下一場開始時自動顯示」。下一場仍在同一團按「開新場」。
5. 旅程結束後按「關閉固定入口」，代碼不再接受觀眾加入。既有場次與帳本繼續依原有權限與保留期限處理。

「結束本場」和「關閉固定入口」必須是兩個明確按鈕。固定入口平時可顯示「等待下一場」，不會自動開始麥克風或扣點。

## 團員體驗

- 掃同一個 QR。尚未開場時顯示團名與等待畫面；正在開場時看到即時字幕；主持暫停／斷線時看到暫停提示；當場結束時顯示等待下一場。
- 下一場開始時，已開著的頁面自動切換到新場並清空上一場畫面；重新開啟同一連結也加入當下場次，不需再掃碼。
- 每團同時只允許一場「尚未開始／直播／暫停」場次，避免觀眾不知該看哪一場。晚到的團員只看到當場的最近字幕；不同場次的字幕不混合。
- 觀眾仍無須登入；固定碼視為入場憑證。失效、關閉或換碼要分別顯示清楚的狀態。

## 資料與連線設計

- 新增 `tour_groups`：團 ID、擁有者、名稱、唯一固定碼、狀態、當前場次 ID、建立／關閉時間。
- `sessions` 新增可空的 `tour_group_id`。既有一般場次與分享連結保持原樣；固定團的每場仍保有自己的場次 ID、逐字稿、整理工作和用量帳本。
- 後端將團的「開新場／結束本場／關閉入口」與當前場次指標在資料庫交易中更新，檢查擁有者並限制同團同時一場。重啟後從資料庫恢復團和當前場次。
- WebSocket 觀眾以固定碼訂閱團，場次切換時伺服器推送新的場次狀態與清空畫面訊息。斷線重連重新查團的當前場次；舊場字幕序號不得用來要求新場補送。
- 代碼需有大小寫正規化、唯一性檢查、猜碼速率限制與換碼／停用能力。換碼後舊 QR 將失效，介面要明確提示主辦方重新分享。
- 每場的逐字稿仍自結束起保存 30 天；刪除某場不會刪團入口，也不會刪其他場或帳本。

## 驗收情境

1. 同一團第 1 天上午、下午、第 2 天各開一場；三場各自有逐字稿與扣點，同一 QR 全程有效。
2. 團員在上一場結束後保持頁面開啟，下一場開始會自動顯示新字幕且不殘留上一場文字。
3. 伺服器重啟後，同一 QR 能回到等待畫面或當前場次；暫停的場次需主持人再按 Start。
4. 同時按兩次「開新場」不產生兩個有效的當前場次；其他帳號不能控制或關閉本團。
5. 團入口關閉、換碼或點數不足都給出對應訊息；沒有收音就不扣點。

優先順序：先完成固定碼／團清單／單一當前場次／等待與切換／重啟恢復；換碼可以隨同入口停用一起完成。暫不開放自選易猜代碼，先由系統產生可口述的 8 碼。

## 早期使用與未來會員分級

固定入口的建立與從該入口開新場，由 `canCreateFixedTours` 控制。目前以 `TOUR_EARLY_ACCESS_EMAILS` 指定早期使用的 Google 帳號；本機已將唯一的登入白名單帳號設為早期使用者。一般登入者仍可開普通單場，不會看到固定入口建立介面；即使日後 `OPEN_SIGNUP=true`，也不會自動開放此功能。既有團的清單與關閉權限維持給擁有者，避免會員等級調整後失去管理能力。

未來導入會員等級時，只需把同一權限判斷改為「帳戶方案達到指定等級，或在早期使用白名單中」，建立與開新場的 API 不需改資料結構。正式 Railway 環境需另設定 `TOUR_EARLY_ACCESS_EMAILS` 為主辦人 Google 登入信箱；本機 `.env` 不會自動同步到 Railway。

目前已完成：固定 8 碼、團清單與 QR、每團同時一場、等待／自動切換、原場次獨立帳本與逐字稿、關閉入口、重啟恢復。自選代碼尚未實作。固定碼可在沒有進行中場次時更換，舊 QR 立即失效；匿名觀眾猜錯代碼超過每分鐘 60 次會被限制。正式上線仍建議在平台層加上用量監控與流量防護。
